# ロットの統合

末尾に「-」が1つ付いたロット（例 `123456-`。追加分）を、「-」の無いロット（`123456`）へ統合する。
決めたことは CANONICAL_DESIGN_DECISIONS.md の D-136（利用者の決定）、D-145〜D-149（第1段階）、D-150〜D-155（第2段階）。

## 決まっていること（D-136）

- 統合の対象は、末尾の「-」1つだけ。`-1`・`-2`・`K`・`.1` は統合しない。「-」付きにしか計画が無いロットは対象外
- 統合するかは人が判断する（統合の画面で行う）。操作できる人は限定しない
- 保存されたロットNo. は変えない。集計・照合のときに、統合後のロットとして扱う（案2）
- 発注数は、「-」の無いロットの値
- 追加分（X-）に面2の計画しか無い場合、その面2の数量を、計算のうえで面1にも数える（データはそのまま）
- 画面のロットNo. は「123456（+123456-）」のように添える
- 実績CSVで候補なしの行に似たロットがあるときは「似たロットNoあり：326611-」と表示するだけ
- 使用するPCは担当者の1台だけ
- 過去の日付の引落（2026-10-15 確定）: 引落の日付は実績の日付のまま。統合した日に引落が出ることはない。
  例: 123456 の実績で 7/10 に揃った 99 は 7/10 に 99 のまま。123456- の実績 1 台（7/15）は、統合の後から 7/15 に +1 として現れ、7月の合計は 100 になる。
  統合や解除で、過去の日付の数字が後から変わってよい

## 保存の形（第1段階、D-145）

- 月次DB の表 `lot_merges`（マイグレーション 014。新しく作る DB は `db/schema.sql`）。1行が「統合されるロット → 統合先」
  - `member_lot`（主キー、例 `123456-`）・`target_lot`（例 `123456`）・`merged_at`・`merged_by`・`note`
  - `member_lot = target_lot || '-'` と「`target_lot` の末尾が `-` でない」を表の CHECK でも確かめる（書き込む関数 `models/lot_merges.py` でも確かめる）
- 統合を解除すると行を消す。統合・解除は操作履歴（「ロット統合」「ロット統合解除」）に残る
- 読む側は `services/lot_merge_service.load_lot_merge_map()` で1回だけ読み、`target_of()`（ロットNo. → 統合後のロットNo.）・`members_of()`（統合後 → 統合しているロット）を使う

## 集計への反映（第2段階、D-150〜D-155）

統合後のロット（統合先のロットNo.）を1つのロットとして評価する。統合していないロットの計算は変えない。
中心は `services/lot_merge_items_service.py` の `_merge_lot_items()`（評価に使う計画の行と、統合の扱い `merge_ctx` を作る）。集計の本体は `services/lot_status_service.py`。

守る約束:

1. 計画の行の `lot_no` は書き換えない。評価に使う行は写しで、元のロットNo. を持ったまま
2. 実績は計画ごとに、**元のロットNo.** と計画No. の組で引く（`226793` と `226793-` のように計画No. を共有する組で、実績を二重に足さないため）
3. 統合されるロットの行の発注数は、統合先の発注数の代表値にそろえる（保存値は変えない）。そのため「発注数不一致」にならない
4. 統合されるロットの行の基板名は、統合先の同じファイルNo. の基板名にそろえる（統合先のそのファイルNo. の基板名が1種類のときだけ）。表記ゆれでファイルNo. が二重に数えられない

追加分の面2を面1にも数える条件（D-157。2026-10-16 に D-151 から変更）:

- 利用者の決定:「面2があるということは、面1もあるとみなす」
- 統合されるロット（X-）の**ファイルNo. ごと**に判断する。X- のそのファイルNo. に面2の計画があれば、X- のそのファイルNo. の面1の数量として、面2の計画の実績（元のロットNo. で引いた値）を使う。X- に面1の計画があるかどうかは問わない
- 二重に足さない: X- のそのファイルNo. に面1の計画と実績もある場合（面2の登録で面1へ自動入力された実績 D-113 など）、**面1の実績は使わず、面2の数量だけを使う**
- 統合後のロットのどこにも、そのファイルNo. の面1の計画が無ければ足さない（新しい (ファイルNo., 面1) を作らない）
- 日付の絞り込み（日々の引落）は、面2の実績の日付で効く

面1を隠す処理（D-8）:

- 集計（ロット進捗チェック・日々の引落一覧・実績レポート・仕掛数量抽出）は、統合後のロットで判定する（統合後のロットのどれかに面2の計画があるファイルNo. の面1を隠す）
- 実績の登録の候補（`list_active_plan_items()`）と、面2を登録したときの面1への自動入力（`find_opposite_side_plan()`）は、元のロットのまま（変えない）

表示（D-152）:

- ロット進捗チェック・日々の引落一覧・実績レポート（とそれぞれの CSV 出力・印刷）のロットNo. の列は「123456（+123456-）」
- どの元のロットの計画かは、ファイルNo. の列の後ろに添える。統合先の計画だけの行はファイルNo. のまま。例: `0553（348588・348588-）`、`0156（326560-）`
- 実績レポートの行の `lot_no` は実績の元のロットNo. のまま（実績修正・NG・仕掛数量抽出で使う）。表示だけ `lot_label`・`file_label` を使う
- 実績レポートの「発注数」は、統合したロットの行すべて（統合先の行も統合される行も）で、統合先の代表の発注数（D-158）
- 完成済みロットの確認の文（右クリック・ダブルクリック・手入力・実績修正）は「ロット 500500（+500500-） は完成済みです…」（D-159）

そのほか:

- 完成済みロットの扱い（D-130）は `evaluate_lot_status()` を通すので、統合後のロットの完成で判定する（どちらのロットNo. で聞いても同じ）
- 生産実績入力の計画一覧の「完成数」は統合後のロットの値。「入力済み」は統合先にそろえた発注数と比べる
- ロット状態の履歴（`lot_status_history`）は、統合後のロット（統合先のロットNo.）で記録する
- 前月からの引き継ぎ（D-154）: 未完了の判定は統合後のロット単位。未完了なら、統合しているすべての元のロットの計画・実績と、統合の行を一緒に写す
- 統合の画面（D-153）: 統合する前に、確認ダイアログで「今の X」「今の X-」「統合後」の発注数・完成数・残りを試算して示す（`preview_merge()`。DB には書かない）

## 実績CSVとの照合（第3段階、D-160〜D-163）

- 候補の集め方: 統合したロットでは、CSV の行のロットNo. が X でも X- でも、X と X- の両方の計画を候補にする（`merge_plan_items_by_lot()`）。候補一覧の「ロットNo.」の列は候補の計画の元のロットNo.。候補が2つ以上のロットにまたがるときは、ヒントに「統合したロットのため…」と出す
- キー: 計画・候補は (計画No., 元のロットNo.) で区別する。実績・重複は候補の元のロットNo. で見る（`match_lot_of()`）。計画No. を共有する X・X- は別の候補として「複数・要選択」になり、自動登録しない
- Shift+S・Shift+Q の条件は変えない。統合で候補が増えると、自動登録の対象が減る（設計どおり）
- 「候補なし」の行で、末尾「-」を付けた／外したロットに計画があれば「候補なし（似たロットNoあり：326611-）」と出す（`find_similar_lot_no()`。表示だけ。「-1」「K」などは対象外）
- 面2を登録したときの面1への自動入力（D-113）と、その置き換えの確認（D-126）、登録の候補の面1を隠す処理は、元のロットの中だけ（統合をまたがない）
