# ロットの統合

末尾に「-」が1つ付いたロット（例 `123456-`。追加分）を、「-」の無いロット（`123456`）へ統合する。
決めたことは CANONICAL_DESIGN_DECISIONS.md の D-136（利用者の決定）と D-145〜D-149（第1段階）。

## 決まっていること（D-136）

- 統合の対象は、末尾の「-」1つだけ。`-1`・`-2`・`K`・`.1` は統合しない。「-」付きにしか計画が無いロットは対象外
- 統合するかは人が判断する（統合の画面で行う）。操作できる人は限定しない
- 保存されたロットNo. は変えない。集計・照合のときに、統合後のロットとして扱う（案2）
- 発注数は、「-」の無いロットの値
- 追加分（X-）に面2の計画しか無い場合、その面2の数量を、計算のうえで面1にも数える（データはそのまま）
- 画面のロットNo. は「123456（+123456-）」のように添える
- 実績CSVで候補なしの行に似たロットがあるときは「似たロットNoあり：326611-」と表示するだけ
- 使用するPCは担当者の1台だけ
- 過去の日付の引落（2026-10-15 確定）: 引落の日付は実績の日付のまま。統合した日に引落が出ることはない。
  例: 123456 の実績で 7/10 に揃った 99 は 7/10 に 99 のまま。123456- の実績 1 台（7/15）は、統合の後から 7/15 に +1 として現れ、7月の合計は 100 になる。
  統合や解除で、過去の日付の数字が後から変わってよい

## 保存の形（第1段階、D-145）

- 月次DB の表 `lot_merges`（マイグレーション 014。新しく作る DB は `db/schema.sql`）。1行が「統合されるロット → 統合先」
  - `member_lot`（主キー、例 `123456-`）・`target_lot`（例 `123456`）・`merged_at`・`merged_by`・`note`
  - `member_lot = target_lot || '-'` と「`target_lot` の末尾が `-` でない」を表の CHECK でも確かめる（書き込む関数 `models/lot_merges.py` でも確かめる）
- 統合を解除すると行を消す。統合・解除は操作履歴（「ロット統合」「ロット統合解除」）に残る
- 読む側は `services/lot_merge_service.load_lot_merge_map()` で1回だけ読み、`target_of()`（ロットNo. → 統合後のロットNo.）・`members_of()`（統合後 → 統合しているロット）を使う
