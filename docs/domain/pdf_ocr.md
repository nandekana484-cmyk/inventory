# PDF 読み取り・OCR（services/pdf_ocr_service.py）

2026-10-09 のコメント軽量化で、コメント・docstring から移した内容。関数名・定数名で参照する。
**調整値と閾値の根拠はここにしか無い。値を変えるときは、ここを読んでから変えること。**
機能の背景は PDF_OCR_FEATURE_NOTES.md。メインメニューの「PDF読み取り」は現在、常に無効（D-85。コードは残っている）。

## 全体の流れ（`extract_pdf_rows()`）

1. pdfplumber で各ページの `extract_text()` を試す（ページの区切りは改行2つ。テキストが無いページは空文字として扱う）
2. 全ページ合計が `_MIN_TEXT_LENGTH_THRESHOLD` 文字未満なら、テキスト層が無い（スキャン画像の PDF など）とみなし、pdf2image で画像化して Tesseract で OCR する
3. 列に分ける
   - OCR: 単語の座標から列を復元する（案A）。ヘッダー行を検出できなければ空白区切り
   - テキスト抽出: 座標が無いので空白区切り（`_split_line_to_columns()`）だけ
4. 信頼度: テキスト抽出は文字化けの心配が無いので常に100。OCR は行に属する単語の信頼度の平均
- 戻り値: method（"text"/"ocr"）・rows（空行は除く）・confidences（rows と同じ件数）・raw_text・page_count
- 外部依存（OS に別途インストール）: Tesseract 本体（`config.TESSERACT_CMD`、日本語データ `config.TESSDATA_DIR/jpn.traineddata`）と Poppler（`config.POPPLER_PATH`）

## 定数と調整値

| 名前 | 値 | 根拠 |
|---|---|---|
| `_MIN_TEXT_LENGTH_THRESHOLD` | 20 | 全ページ合計がこの文字数未満なら OCR にする。テキスト PDF でも空白ページなどが混ざるので、0 ではなくある程度の閾値にした |
| `_OCR_LANGUAGES` | "jpn+eng" | 96コードなどの英数字と、部品名などの日本語が混ざるため |
| `_MAX_OCR_WORKERS` | 3 | 事務用 PC（Core i5 相当、コア数が限られる想定）で負荷をかけすぎないため。実測では1ワーカーの OCR（OpenCV の前処理＋Tesseract）で CPU を使い切るので、コア数以上に並列化しても速くならない。ほかの作業を妨げないよう、コアを使い切らない余裕を残す |
| `_BACKPRESSURE_EXTRA_FUTURES` | 2 | 未回収の OCR がワーカー数＋この数に達したら、画像化を止めて1つ終わるのを待つ。+2 は、ワーカーが手待ちにならないよう、処理中のページに加えて次にすぐ渡せる画像を少し持っておくため（余裕が無さすぎると速度が落ちる） |
| `_PART_NO_PATTERN` | `^96\d{5,6}$` | 96コード＝"96" で始まる7〜8桁の数字（既存の BOM・在庫と同じ想定。例: "96000123"）。名称・数量を誤判定しないよう、セル全体で一致を判定する |
| `_MIN_DETECTED_COLUMNS`〜`_MAX_DETECTED_COLUMNS` | 2〜30 | 検出した列数がこの範囲の外なら、ヘッダー行の検出に失敗した（表ではない・単純すぎる／複雑すぎるレイアウト）とみなし、空白区切りにする。1列（実質、列に分かれていない）や、隙間のクラスタリングが細切れになりすぎた誤検出を弾く安全弁 |
| `_COLUMN_GAP_MEDIAN_MULTIPLIER` | 3 | ヘッダー行の単語間の隙間の中央値（列内の文字間隔の典型値とみなす）のこの倍を超える隙間を、列の区切りとする。実際の表形式のテスト PDF（10列）では、列内の隙間が数px、列間の隙間が250px超で、2〜30倍なら同じ結果だった。余裕を持たせて3 |
| `_ROW_GAP_HEIGHT_RATIO` | 0.6 | 直前の行との代表 Y 座標の差が「直前の行の文字の高さ×この倍率」を超えたら別の行。文字の高さとの比にするのは、フォントや dpi が変わっても、同じ行のセルはほぼ同じ Y に並び（差は文字の高さよりずっと小さい）、行が変われば少なくとも文字の高さ程度の差が出るため。実データで 0.6 で正しく分かれた |
| `_DPI` | 300 | 下の「dpi と psm」 |
| bilateralFilter | d=9, sigmaColor=75, sigmaSpace=75 | 下の「前処理」 |
| adaptiveThreshold | ブロックサイズ 35, C 11 | 下の「前処理」（以前の 31, 15 から、ブロックサイズを大きく・C を小さくした） |
| CLAHE | clipLimit=2.0, tileGridSize=(8, 8) | 値の根拠はコメントに無かった（未確認） |
| 傾き補正の下限 | 0.5度 | これ未満なら回転しない。傾いていないきれいな画像を回転・補間で劣化させないため（合成テスト画像などの精度を保つ） |
| ワーカー数（CPU 数が取れないとき） | 2 | `os.cpu_count()` が None を返す環境（まれ）では2とみなす（既存のフォールバックと同じ考え方） |

## dpi と psm（`_extract_lines_via_ocr()`、2026-09-25）

- 当初は高速化のため 150dpi に下げた（pdf2image の既定 200dpi より低い）。単純な1ブロックの部品リスト風テストデータでは、認識行数が変わらなかったため
- 実際の運用に近いレイアウト（タイトル4行＋10列の罫線付き表）で検証し直すと、150dpi では文字が小さすぎて OCR が機能しなかった。タイトルもデータ行も、ばらばらの1文字や意味の無い断片になった（例: 「月次基板構成数チェックリスト」が「awigemserx ャ ク リ ス ト」になる）。200dpi でも改善は限られた
- 300dpi で、タイトル・96コード・数量・日付などがほぼ完全に認識できた（実用レベル）ので、精度を優先して 300dpi にした
- `--psm` は指定しない（既定の 3）。同じ検証で、4 は 3 と同じ結果、6 は罫線を文字と誤読してデータ行がほぼ全滅した

## 前処理（`preprocess_image_for_ocr()`）

順序: グレースケール → 傾き補正 → ノイズ除去 → コントラスト強調 → 二値化。地の傾きとノイズを先に整えてからコントラストを上げることで、ノイズが強調されるのを避ける。

1. グレースケール: OCR に色は不要
2. 傾き補正（`_deskew()`）: スキャン時のわずかな回転は認識精度を大きく下げる。Otsu の二値化で文字らしい画素を取り、その全画素の外接矩形（`cv2.minAreaRect`）の傾きを画像全体の傾きとして回転する（広く紹介されている標準的なレシピ）。ハフ変換の直線検出も検討したが、罫線がはっきりしない文書では不安定になりやすく、外接矩形の方が単純で頑健。`minAreaRect` の角度は [-90, 0) で、長辺・短辺の取り方で符号の意味が変わるので、-45度を境に補正の向きを変える
3. ノイズ除去: `cv2.bilateralFilter`（2026-09-25 に見直し）
   - 以前は Non-Local Means（`cv2.fastNlMeansDenoising`）で、前処理全体の約97%（1画像あたり約1.3秒）を占める最大のボトルネックだった
   - `cv2.medianBlur`（カーネル 3・5・7）を試したが、傾き・低コントラスト・ノイズを加えた劣化画像のテストで、明らかに精度が落ちた（行の脱落・誤認識が増えた）ので不採用
   - bilateralFilter は、エッジ（文字の輪郭）を保ちながら平坦な部分をならす点で fastNlMeansDenoising に近く、計算は大幅に軽い（1画像あたり 1.3秒 → 0.01秒未満）。同じ劣化画像のテストで同等の結果だった
   - d=9（近傍の直径）・sigmaColor=sigmaSpace=75 は、OpenCV の公式ドキュメントが「中程度〜強めのノイズ除去」の例として挙げる値をそのまま使った
4. コントラスト強調: CLAHE。単純なヒストグラム均等化（`cv2.equalizeHist`）は画像全体を一様に引き伸ばすので、「用紙の一部だけ影で暗い」ような局所的な明暗差に効きにくい。CLAHE はタイルごとに均等化するので、局所的な低コントラストに効く
5. 二値化: 適応的二値化（`cv2.adaptiveThreshold`、ガウシアン重み）。Tesseract も内部で二値化するが、照明ムラのある画像では先に適応的二値化しておく方が安定しやすい。ブロックサイズと定数 C は、ノイズ除去の後に残るわずかな濃淡差で誤って二値化しないよう、単純なガウシアンブラー前提だった値（31, 15）より、ブロックサイズを大きく・C を小さくした

## 座標による列の復元（案A、2026-09-25）

- `_group_words_into_line_records()`: `image_to_data()` の結果を (block_num, par_num, line_num) ごとにまとめ、単語の座標（left/top/width/height）付きの行レコードにする（以前は (テキスト, 平均信頼度) だけを返す `_group_words_into_lines()` だった）。conf == -1（単語ではなく、行・段落・ブロックの構造情報だけの要素）と空の単語は読み飛ばす。日本語は `image_to_data()` で1文字ずつ別の単語になりやすく、空白区切り（`_split_line_to_columns()`）では日本語の部分が細切れになった。これが座標で列を復元する方式を作った理由
- `_group_line_records_into_rows()`: 罫線付きの表（主な対象の帳票）を tessdata_fast の Tesseract で OCR すると、ページ分割が罫線をブロックの境界と解釈し、1つの見た目の行の各セル（例: ヘッダーの「シリーズ」「コード」「型名」）が別々の行として認識された。そのままでは列境界の検出が1セルだけの行で行われてしまうので、Y 座標で見た目の行にまとめ直す。まとめるときは各行レコードの先頭の単語の left 順に並べる（列の順を保つ）
- `_detect_column_boundaries()`: 単語を left 順に並べ、隣り合う単語の隙間（前の単語の右端から次の単語の左端）を求め、中央値の `_COLUMN_GAP_MEDIAN_MULTIPLIER` 倍を超える隙間で列を分ける。中央値が0以下（文字が密着・重複）でも誤分割しないよう、閾値は最低1px
- `_assign_words_to_columns()`: 単語の中心 x と各列の中心の距離が最も近い列に割り当てる。範囲内かどうかで判定すると、描画位置のわずかなずれでどの列にも入らない単語が出る。同じ列の単語はスペースを挟まずにつなぐ（例: "図面"+"001" → "図面001"）。Tesseract が1つのセル（日本語＋数字など）を複数の単語に分けることがあり、テスト PDF ではスペース無しの方が元のセルに近かった。英語の複数語（"PART NAME"）は例外だが、対象は日本語主体の帳票（96コード・図名・型名）
- `_find_header_row_index()`: 検出した列数が許容範囲内の行のうち、列数が最も多い行（同数なら上の行）をヘッダー行にする
  - 当初は先頭行をヘッダーとみなしていたが、想定レイアウト（タイトル4行＋10列の表）で、表の前のタイトル行の文字間隔から誤った列境界ができ、表全体がその境界で分けられた
  - 試して失敗した方式: (1)「次の1行と列数が近ければ採用」→ タイトル行どうしが偶然近い列数に分かれることがあった。(2)「後続の各行が自分の隙間から検出する列数が近いか」の連続長 → データ行（値が短く隙間がほぼ均等）は単独では中央値の閾値がうまく働かず、ほぼ常に1列に潰れた。(3)「候補の境界を後続の行に当てはめ、一定数以上の列が埋まるか」→ 閾値を低くするとタイトル行由来の境界でも多くの行が満たし、ページの上にある行ほど後続の行が多くて有利になる偏りがあった
  - タイトル行（文章の文字間隔のばらつきによる偶然の分裂）は最大5列程度、表のヘッダー（項目名の境界がはっきりした罫線付きの表）は10列にきれいに分かれた。差が十分にあるので、最大値で選ぶのが最も頑健だった
- `_build_rows_for_single_page()`: ヘッダー行より前の行（タイトルなど、表の一部ではない行）は空白区切りのまま。ヘッダー行以降（ヘッダー行を含む）に列境界を当てはめる
- `_build_rows_from_line_records()`: 行レコードの座標はページ画像ごとの相対座標で、ページをまたいで比べられない。以前は全ページをまとめて処理していて、別ページの似た座標の行やセルが1つにまとまった（81ページの PDF が8行に潰れた）。page_no でページごとに分け、独立に処理してページ順につなぐ
  - ヘッダーは各ページで独立に探す（ページをまたいで状態を渡さずに済む）。そのため、ヘッダーが1ページ目にしか無い帳票では、2ページ目以降は空白区切りになり精度が下がる。複数ページにまたがる表は各ページにヘッダーを再掲するのが一般的で、想定レイアウトもそう。1ページ目の列境界を全ページに使い回す案も検討したが、ページごとに画像のわずかな伸縮や余白の差があり得るので、各ページの実測から検出する方式にした。ヘッダーを繰り返さない帳票が問題になったら再検討する

## 並列化（`_extract_lines_via_ocr()`、`_ocr_one_page()`、2026-09-25）

- ページごとの前処理・OCR は独立なので、`ProcessPoolExecutor` でページ単位に並列化する。OpenCV の前処理も Tesseract も CPU バウンドで、GIL のあるスレッドでは並列にならないので、プロセスにした
- 1ページだけの PDF は、プロセスの起動と重いモジュール（cv2・numpy・pytesseract）の再 import の方が処理より重くなりうるので、並列化しない
- 画像化と OCR を重ねる: 以前は全ページを一括で画像化してから OCR していて、ページの多い PDF（実データで81ページ）では画像化の時間がそのまま積み上がった。`convert_from_path(first_page=..., last_page=...)` で1ページずつ画像化し、終わったページから `submit()` で OCR に回す。`map()` は入力を先に全部そろえる必要があるので合わない
- ページ順の保証: 完了順は投入順と一致しないので、Future を投入順のリスト（page_futures）に持ち、全ページの投入後にその順で `result()` を呼ぶ。バックプレッシャー用の集合（pending_futures）は別なので、順序には影響しない
- バックプレッシャー: 画像化が OCR よりずっと速い場合（ノイズの多いスキャン画像で OCR が遅いときなど）、未回収の Future とその画像が際限なく積み上がり、メモリを圧迫した。pending_futures がワーカー数＋`_BACKPRESSURE_EXTRA_FUTURES` に達したら、`wait(..., return_when=FIRST_COMPLETED)` で1つ終わるまで待つ。`wait()` を呼ぶまで集合を更新しないので、完了済みの Future が残ることがあるが、次の `wait()` ですぐ done として返るので実害は無い
- 別プロセスには、親の `_configure_tesseract()` の設定（tesseract_cmd・TESSDATA_PREFIX）が引き継がれない（Windows の spawn は新しいインタプリタでモジュールを import し直すだけ）。ワーカーで設定し直す
- 引数と戻り値は pickle できる型だけにする（PIL Image は pickle できる）
- UI との関係: `ui.pdf_ocr_import_window` が threading.Thread でこの関数を呼ぶ。スレッドは UI を止めないため、プロセスプールは複数コアに分散するためで、目的が違い両立する。この関数自体は全ページが終わるまで戻らない同期関数

## そのほか

- tessdata の場所は環境変数 `TESSDATA_PREFIX` で渡す（`_configure_tesseract()`）。`image_to_string()` に `config='--tessdata-dir "<path>"'` を渡す方式では、pytesseract が config をトークンに分けるときに手で付けた引用符がそのまま残り、末尾に引用符の付いた不正なパスとして解釈されて読み込みに失敗した
- `image_to_string()` ではなく `image_to_data()` を使うのは、単語ごとの信頼度（0〜100）を取り、行の平均信頼度として UI で低い行を示すため
- 96コードの判定（`_find_part_no_in_row()`）: 行の中で最初に一致したセルを使う（名称・数量が同じ桁数の "96" 始まりの数字になることはほぼ無いので、複数一致の警告はしない）。判定の前に NFKC で正規化する（2026-09-25）。jpn+eng の OCR が数字を丸数字（例: "①" U+2460）に誤認識することが実データであり、NFKC は通常の数字に変える。テキスト抽出と OCR の両方が通る唯一の入口なので、ここで正規化すれば両方に効く（PDF に全角数字で96コードが入っている場合にも効く）。`_PART_NO_PATTERN` 自体は変えていない
- 在庫との照合（`match_against_inventory()`）: inventory_stock に登録済みの96コード（当部署で在庫管理している部品）を含む行だけを残す。96コードが無い行（見出し・ノイズ）と、登録されていない96コード（他部署の部品と想定）の行は除外し、件数だけを数える
- 列分解（`_split_line_to_columns()`）は空白・タブの連続で分ける素朴な実装。実運用の PDF レイアウトが分かったら、固定長・区切り文字・正規表現などへの差し替えが必要になる可能性が高い
- CSV の書き出し（`write_rows_to_csv()`）は、行ごとに列数が違ってもそのまま書く（空欄で埋めない）
- ログ（2026-09-25）: 開始・完了・エラーを `config.LOG_DIR/pdf_ocr_YYYYMMDD.log` に記録する専用ロガー。ワーカーの異常終了（BrokenProcessPool など）は UI でダイアログが出るだけでログに何も残らなかったため追加した。ほかのロガー（services/bom_service.py など）はハンドラを設定しておらず、実質どこにも出ていない。このロガーは FileHandler を設定し、propagate=False でルートロガーへの二重出力を避ける。起動したまま日付が変わったら、ログを出すときにハンドラを張り替える。ページ数（`get_pdf_page_count()`）は、本処理が途中で例外を出してもログに残せるよう、UI 側が別に数える
