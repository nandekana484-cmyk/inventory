# 基板丁数の対応表（現場アプリ向け）

決めた経緯は `CANONICAL_DESIGN_DECISIONS.md` の D-191（§66）。実装は `models/board_teitori_map.py`・`services/board_teitori_service.py`・`services/board_teitori_runner.py`。

## 何のための表か

現場アプリが「計画ごとの丁取り数」を引くための、master.db の対応表。丁取り数は計画に入っておらず、計画の (ファイルNo., 実装ライン) から BOM TSV の **K行**（基板自身の行）の96コードを引き、基板丁数マスター（`parts_attributes`）の `teitori` を見る。この流れを既存アプリが先に済ませておく。

## 現場アプリが読むもの：ビュー `v_board_teitori`

master.db の `v_board_teitori` を読む（表 `board_teitori_map` は直接読まない）。

| 列 | 内容 |
|---|---|
| `setup_file_no` | 正規化したファイルNo.（下の規則） |
| `mounting_line` | 正規化した実装ライン |
| `part_no` | K行の96コード（TSV から K行を引けなかった status では NULL） |
| `teitori` | **status が `ok` のときだけ、1以上の整数**。それ以外は NULL |
| `status` | 下の8種類 |
| `fetched_at` | その組を TSV から引いた日時（`YYYY-MM-DD HH:MM:SS`、そのPCのローカル時刻） |

### status の8種類

| status | 意味 | teitori |
|---|---|---|
| `ok` | TSV が1つに決まり、K行の96コードが1つに決まり、基板丁数マスターに1以上の整数の丁取り数がある | 整数 |
| `tsv_not_found` | ファイルNo.に当たる BOM TSV が共有フォルダに無い（.xlsx だけの場合も含む。.xlsx は読まない） | NULL |
| `ambiguous_tsv` | TSV の候補が2つ以上あり、1つに決まらない（例：`432_A4-1` と `432_A6`） | NULL |
| `read_error` | TSV を読めなかった（文字コード・破損したヘッダーなど） | NULL |
| `no_k_row` | その実装ラインに K行（セットアップ部品種別 = K）が無い | NULL |
| `multi_k` | その実装ラインに、異なる96コードの K行が2つ以上ある | NULL |
| `code_not_in_master` | K行の96コードが基板丁数マスターに無い | NULL |
| `teitori_invalid` | 基板丁数マスターに有るが、丁取り数が空・0以下・小数・数でない | NULL |

`code_not_in_master`・`teitori_invalid` は、表には保存せず、ビューが基板丁数マスターと結び付けて返す。**基板丁数マスターを変えると、TSV を読み直さなくてもビューの結果が変わる。**

## 正規化の規則（キーの作り方）

表のキー（`setup_file_no`, `mounting_line`）は、既存アプリの `models/production_side_master.py` の関数で正規化した値。**現場アプリも同じ規則で正規化してから引くこと。**

- 共通：NFKC 正規化（全角→半角）→ 前後の空白を除く → 大文字にする
- `setup_file_no`：数字だけなら、**4桁になるまで前に 0 を足す**（`4` → `0004`、`161` → `0161`）。英数字を含む値（`T458` など）は、共通の規則だけ
- `mounting_line`：共通の規則だけ

計画の取り込みは変えていない（`kitting_plan_items` には CSV の値が、前後の空白を除いただけで入っている）。正規化は、この表のキーを作るときだけ行う。ファイルNo.・実装ラインのどちらかが空欄の計画は、表に入れない。

## 対象の計画

月次DB の `kitting_plan_items` のうち `COALESCE(is_active, 1) = 1 AND COALESCE(delete_flag, 0) = 0`（完了済みのロットも含む）。`delete_flag` の列が無い古い版の DB では `is_active` だけで判定する。

## 取得のタイミングと、行が無い組

| タイミング | 内容 |
|---|---|
| 計画CSVの取り込みが成功した後 | 今の月次DB の組のうち、表に無い組・TSV の更新日時が変わった組・status が `ok` 以外の組だけを引く（背景） |
| 前月引き継ぎが完了した後 | 同上 |
| 手動の再取得 | メインメニューの「基板丁数の対応表を再取得」。db フォルダの下のすべての月次DB（既定DB を除く）から組を集め、全部引き直す |

バッチの復元は、今のアプリに画面からの操作が無いので、取得を足していない。復元された計画の組は、次の取得（取り込み・引き継ぎ・手動）で拾われる。

- **取得が終わるまでは、行が無い組がありうる。** 現場アプリは、**行が無い組と、知らない status は「不明」として扱う**こと（status は今後増えることがある）。
- 行は消さない。計画から無くなった組の行も残る。
- 取得は1つずつ走る。走っている間に次の依頼が来たら、終わった後に1回だけ走る。
- BOM の共有フォルダを読めない（TSV が1つも見えない）ときは、取得を止めて何も書かない。全組を `tsv_not_found` で上書きしないため。この失敗だけは、アプリの画面にエラーが出る（背景の取得はメイン画面が、手動の再取得はその場で。「ネットワークを確かめてから『基板丁数の対応表を再取得』を押してください」）。現場アプリは、表の行が古いままになりうる（`fetched_at` で分かる）。共有フォルダ以外の失敗は、背景ではログに残るだけ。
- 既定DB（未選択）のときは、ふだんの取得は何もしない。

## master.db の扱い

- ジャーナルモードは **delete のまま**（WAL にしない。共有フォルダ越しの WAL は安全でない）。
- 書き込みは **50組以下ずつ**の短いトランザクション（`INSERT ... ON CONFLICT DO UPDATE`）。書き込みのコミットは、読んでいる接続の共有ロックが外れるまで待つので、現場アプリは**短く読んで接続を閉じる**こと（読み取り専用の URI `mode=ro` と `PRAGMA query_only = ON`、待ち時間を短く）。
- 月次DB を読むときは、`file:...?mode=ro` と `PRAGMA query_only = ON` で開く。形の確認・マイグレーション・`config.DB_PATH` の切り替え・ロックファイルの操作はしない。
- `master_merge_service`（他PCのマスタを取り込む）の対象には入れていない。表とビューは使うときに作る（マイグレーションは無い）。ビューの定義は、作るときに今の定義と比べ、違うときだけ作り直す。

## K行の探し方

`BOMService._calculate_bom` と同じ規則：`セットアップ部品種別 == "K"` で、実装ラインが一致する行の96コード（生産面では絞らない）。ただし実装ラインは、キーと同じ正規化をして比べる。
