# 実績CSV取込のステージング一覧（ui/production/production_import_staging_window.py）

2026-10-09 のコメント軽量化で、コメント・docstring から移した内容。関数名で参照する。
生産実績入力画面側のルールは `docs/domain/production_entry.md`。

## 画面の構成と連携

- 右ペイン＝登録待ちの保留行（`pending_csv_import_rows`）、左ペイン＝右で選んだ行の候補（`find_matching_plan_items()` で再照合）。NG入力・仕掛展開画面と同じ配置規則（左＝操作・詳細、右＝一覧）
- 候補をダブルクリックすると、親（`KittingProductionEntryWindow`）の `load_staged_row()` で記入欄に転記する。以前は `ui.kitting.plan_candidate_dialog.select_plan_candidate_by_lot()`（モーダルダイアログ＋コールバック）を使っていたが、親への参照を持っていたので直接呼ぶ形にした。親の `load_staged_row()` はウインドウの前面やフォーカスに依存しない
- 親の画面に触るのは公開メソッド `load_staged_row()`・`refresh_after_external_registration()`・`confirm_overwrite_if_existing()` だけ（段階3b、2026-10-13。以前は親の `_pending_csv_row_removal`・`_perform_registration()` などを直接使っていた）
- `ui.kitting.plan_candidate_dialog` の並べ替え・ハイライト判定（`_sort_candidates_by_closeness()`・`_is_large_qty_diff()` など）は、重複させないため直接 import して使う。`plan_candidate_dialog` 自体は NG入力画面がまだ使うので変えていない
- 登録完了の検知: `_confirm_candidate()` で作った remove_callback を `load_staged_row()` で親に渡し、親の `_perform_registration()` が実績の登録成功時に呼ぶ。即時登録・一括登録では、この画面の `_register_staged_row()` が呼ぶ。この画面から DB をポーリングはしない
- 候補は DB に保存せず、表示のたびに再照合する（計画の変更に追随するため）。登録・除外が決まった保留行は、即座に物理削除し、履歴は残さない
- 左右の幅はドラッグで変えられる（2026-10-15、D-123。`ttk.Panedwindow`）。初期位置は以前の pack 配置と同じ「左ペインの必要幅」で、余った幅は右ペインだけに回す。ttk の Panedwindow にはペインごとの最小幅が無いので、ドラッグ・サイズ変更の後に `_clamp_pane_sash()` で左右とも300px以上に戻す（サッシュの太さは style から引けないので配置から測って覚える）
- 候補一覧から実績修正画面を開いて閉じたら、その行の「状態」列を判定し直す（2026-10-15、D-122。`services/staging_eligibility.reevaluate_staged_row()`）。判定は一覧を開くときと同じ手順で、「同じ計画への重複」を数えるため一覧の全行を照合し直すが、表示を変えるのはその行だけ（ほかの行の状態・選択位置は変えない）

- ロットの統合（2026-10-16、D-160〜D-163）: 統合したロットでは X・X- の両方の計画を候補にし、計画・候補は (計画No, 元のロットNo) で区別する（実績・重複は候補の元のロットNoで見る。`lot_merge_service.match_lot_of()`）。「候補なし」の行に、末尾「-」を付けた／外したロットの計画があれば「候補なし（似たロットNoあり：326611-）」と出す（状態は変えず、表示だけ。`staging_status_label()`）。詳細は docs/domain/lot_merge.md

## 自動登録の判定（`evaluate_auto_register_eligibility()`）

一覧の状態表示・Shift+S・Shift+Q が以前は別々の基準で判定していたため、1つの関数にまとめた（D-101）。優先順位と意味:

1. 候補なし: lot_no が一致する計画が1件も無い
2. 製品名の不一致: lot_no は一致するが、製品名が一致する候補が無い（以前は「候補あり（要選択）」に含まれていた）
3. 候補が複数: 製品名まで一致する候補が2件以上（どれかは人が選ぶ）。(計画No, 元のロットNo) の種類で数える（統合したロットで計画Noを共有する X・X- は2件。D-161）
4. 既に実績あり: その計画 (kitting_list_no, lot_no) に実績が1件以上ある（黙って上書きしないため）
5. 同じ計画への重複: 同じ計画を候補とする保留行がほかにもある（どれを登録するかは人が判断する）
6. 面2待ち／生産面マスター未登録: 候補の計画が面1だけで、生産面マスターの分類が b・c
7. 数量の不一致: 計画数と CSV の実績数が完全一致しない
8. 日付を解釈できない: 払い出し日・生産予定日のどちらかが解釈できない（安全側で登録できない側とする）
9. 日付の差が許容を超える
10. 登録可: 差が1日以内なら Shift+S、2日以上・許容日数以内なら Shift+Q のみ

- 戻り値 `(status, reason, candidate, date_diff)`: candidate は単一の候補に解決できたときだけ入る。date_diff は計算できたときの日数（許容を超えて不合格でも入る）で、一覧で Shift+S / Shift+Q の表示を分けるのに使う
- 一覧の状態（`_load_staged_rows_from_db()`）は、最も広い Shift+Q の許容日数（4日）で判定してから、date_diff で Shift+S / Shift+Q に分ける

### 日付の差の計算（`_date_only_diff_days()`）

- 日付だけで比べ、時刻は無視する。以前の `_compute_date_diff_days()` は時刻を含む経過時間を切り捨てていたため、暦日の差とずれた。実データの生産予定日には全件 0時以外の時刻がある。例: 払い出し日 2026-07-23・生産予定日 2026/07/21 23:50 は暦日で2日だが、経過時間では1日10分なので1日になっていた
- 日付の解釈（`_parse_flexible_date()`・`_parse_plan_start_datetime()`）は ui.kitting.plan_candidate_dialog のものを使い、形式の解釈を1か所に集める
- 払い出し日は実運用で `"2026/3/18"`（スラッシュ区切り・ゼロ埋めなし）。以前の解釈は `"%Y-%m-%d"` しか受け付けず、`is_auto_confirmable()` が常に False になっていた（修正済み）

### `is_auto_confirmable()` の置き場所

- 調査時の指示は services/production_import_service.py だったが、日付の解釈に ui.kitting.plan_candidate_dialog を使うため、services に置くと services から ui への依存になる。呼び出し元もこのファイルだけなので、ここに置いた（`docs/refactoring_plan.md`「業務ロジックが ui/ にある」）

## 候補一覧の色

- 数量差・日付差が大きい候補（`_is_large_qty_diff()`: 実績数の20%超、`_is_large_date_diff()`: 3日以上）は黄・オレンジ。両方なら赤（large_diff_both）を単独で付ける（タグの重ね合わせの優先順位があいまいになるのを避けるため）
- 自動確定できる候補（緑、数量差0かつ日付差1日以内）は、閾値が重ならないので large_diff 系と同時には該当しない。念のため最優先で判定する
- 製品名不一致は赤（`ui/common/highlight_colors.MISMATCH_RED`）で、ほかのすべての条件より優先する（「同じ行に複数の条件が当てはまるときは、製品名不一致を優先する」という要求）
- 登録済みの候補は文字色をグレーにする。背景色と別の軸なので、ほかのタグと重ねて付ける

## キー操作

- Shift+S・Shift+Q はウインドウ全体に bind する（D-84、2026-10-06）。tree に bind すると、tree にフォーカスがあるときしか発火しない。Tk の bindtags により、子ウィジェットのイベントはトップレベルの bind まで伝わる。tree にも bind すると二重に発火するので、tree には bind しない
- Shift+Q（D-101、2026-10-08）: 対象は選択中の行だけで、日付の許容日数だけを1日→4日に緩める。最初の Shift+Q（D-97）は選択に関係なく全行を対象にしたが、利用者の意図は「照合条件を緩めること」で、選択範囲を無視して登録できるのは危険と判断され、同じ日に取り消した（D-100）
- CapsLock がオンだと Shift+Q の keysym が小文字になるので、`<Shift-Q>` と `<Shift-q>` の両方を bind する（D-97 で確認）
- 開いた直後に `self.tree.focus_set()` しないと、どのウィジェットにもフォーカスが無く Shift+S が効かない

## 即時登録（右クリック）と一括登録

- 右クリック＝確認ダイアログなしで即時登録、ダブルクリック＝親の画面へ転記（通常の登録フロー）
- 即時登録を禁止する候補（2026-10-08、D-115）: 登録済みの候補（誤った上書きを防ぐ。修正はダブルクリックで実績修正画面から）と、数量が違う候補（`_is_qty_mismatch()`）。メニューは作らず、理由を表示して何もしない（この画面にはもともと右クリックメニューが無いため）
- 確認ダイアログの省き方: 確認は親の `_start_registration()` にある。即時登録・一括登録（`_register_staged_row()`）はそこを通らず、`services/production_entry_service.py` の `register_actual_and_ng()` を直接呼ぶ。完了文は戻り値から `format_registration_message()` で作る（親の画面と同じ文言）
- NG は登録しない（`save_qty_by_side={}`）。自動確定の要件は実績数量と日付だけで、NG 欄に別の計画の値が残っていても使わないため
- 即時登録後の数量差チェック（2026-09-24）: 右クリックは数量の一致を要求しないので、計画数と違う登録が起こりうる。その場合は完了メッセージの代わりに「数量を修正しますか？」と尋ね、「はい」なら計画を開き直して記入欄に実績数を入れる（訂正して再登録すると上書きされる）。以前は完了メッセージの内容を `showinfo()` を一時的に無効にして捕まえていたが、段階3bで戻り値から作るようにした
- 完了・数量差ダイアログの parent はこの画面にする（2026-10-07）。生産実績入力画面にすると、閉じたときにそちらが前面に戻り、一覧への復帰が上書きされた（ダブルクリックからの登録では順序の関係で起きなかった）
- ~~面2の登録で面1の既存の実績が置き換わるときの確認（D-126）~~: 2026-10-19 に削除した（D-169。面1に実績を書かなくなったため、`ui/production/opposite_side_overwrite_dialog.py` も削除）
- ロットが完成済みの計画（2026-10-15、D-130）: 候補には残すが、Shift+S・Shift+Q では登録しない（状態「要確認（ロット完成済み）」、除外の理由「ロット完成済み」）。候補一覧では「自動確定可能」の緑にしない（D-132）。一括の中で前の行の登録によって完成した場合も、登録の直前にもう一度確かめて除く。右クリックの即時登録は、完成済みであることと登録後の実績の合計を示して確認する
- 実績修正画面で取り消して登録待ちに戻した行は、`add_restored_row()` で開いている一覧に足す（D-129。状態は `reevaluate_staged_row()`）
- 重複判定の日付（D-134）: `upsert_pending_csv_import_row()` は「2026/7/14」「2026/07/14」「2026-07-14」を同じ日付とみなす（`_same_report_date()`。比べるときだけそろえ、保存値は変えない）
- 一括登録（`_execute_bulk_register()`）
  - 非同期にはしない。1件の登録は DB 書き込み数件で、数十〜百件なら体感できる遅延にならないと判断した
  - 行ごとに lot_status_history を記録すると1件あたり数十 ms かかり、100件で数秒になるので、最後にロット単位でまとめて記録する（2026-09-30）。1ロットの失敗がほかを止めないよう、ロットごとに try/except する
  - 親の画面は行ごとに更新せず、最後に1回だけ更新する（段階3b）。登録したロットの計画一覧の行を更新し、最後に登録まで進んだ行の計画を表示する。行ごとの登録は親の画面の状態に依存しないので、行ごとに更新する必要は無い
  - 終わったら「処理した範囲の直後の行」を選ぶ。次にどこから作業を再開すればよいか分かりやすいため（2026-09-24）。範囲が末尾まであれば、直前の行を選ぶ
- 登録後の選択（`_make_remove_callback()`、2026-10-07）: ダブルクリック・右クリック・Shift+S のどれで登録しても、次の行（無ければ前の行）を選ぶ。以前は右クリックだけが次の行を選んでいた

## 一覧から外した行の扱い

| リスト | 内容 | DB の行 | CSV の理由欄 |
|---|---|---|---|
| 登録不可（`_unregistrable_rows`） | 機械判定の「候補なし」と、人が「候補なしとする」を選んだ行 | 機械判定分は CSV 出力時に削除。人の判断分は即座に削除 | 固定の文言（`REASON_NO_CANDIDATES`） |
| 不一致（`_mismatched_rows`） | 人が「不一致として除外」した行 | 除外した時点で削除 | 行ごとの自由記述（空欄なら既定の文言） |
| 登録済み（`_already_registered_rows`） | 取込時に同じ数量で登録済みと判定された行 | もともと保存されていない | — |

- 人が「候補なしとする」行を即座に削除するのは、以前 CSV 出力時にだけ削除していたため、再度開くと再照合で候補が見つかり、登録待ち一覧に復活した不具合があったから（2026-09-23 修正）。機械判定の行は候補が無いので復活しない
- 人の判断と機械判定で理由の文言を分けなかったのは、登録不可リストが「理由は固定の1種類」という前提の設計で、分けるには行ごとに理由を持つよう拡張する必要があったため
- 「候補なしとする」は自由記述が無いので、誤クリック防止の確認だけ挟む（「不一致として除外」は理由の入力が実質的な確認になる）
- 登録済みリストの右クリックは「通常の一覧に戻す」だけ。戻した後は通常の一覧の操作で対応できるので、専用の2操作は作らなかった。戻すときは DB に書き戻して全件を読み直す（まれな訂正操作なので性能は問題にならない）

## 閉じるときの確認（`_on_close()`）

- 不一致リストは DB から削除済みで、メモリにしか無い。残っていれば CSV 出力を促す（ブロッキング、閉じる前）。「いいえ」なら失われることを承知で閉じる。ファイル選択をキャンセルしたら閉じない
- 未登録の保留行は DB に保存されているので、閉じても失われない（「実績CSV取込状況」から再開できる）。閉じた後に、自動で消える案内を出すだけ（messagebox は閉じる操作を妨げるので、枠だけの Toplevel と after() で消す）
- 登録不可リストは DB に残っていて、再度開けば同じ内容が再構築される（理由も固定の文言）ので、確認しない
