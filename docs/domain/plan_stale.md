# 古い計画の判定（月次DB のビュー v_plan_stale）

決めた経緯は `CANONICAL_DESIGN_DECISIONS.md` の D-193（§68）。定義は `models/plan_stale_view.py`、マイグレーションは `db/migrations/m016_add_plan_stale_view.py`（月次DB の版 16）。

## 何のためのビューか

計画を出し直してキッティングNo.が変わると、古い計画が `is_active = 1` のまま残る。既存アプリは、生産実績入力の計画一覧の「古い計画を隠す」（D-192）で画面から隠す。現場アプリは月次DB を読み取り専用（`mode=ro`）で読むので、同じ判定をビューにして読めるようにした。**判定の決まりはこのビューの1か所だけ**で、既存アプリの画面もこのビューを読む（Python 側に同じ判定は無い）。

## 現場アプリが読むもの

月次DB の `v_plan_stale`。1行 = 有効な計画1つ（`COALESCE(is_active,1)=1 AND COALESCE(delete_flag,0)=0`）。キーは `(kitting_list_no, lot_no)`（`lot_no` が空の計画は `''`）。

| 列 | 内容 |
|---|---|
| `kitting_list_no`, `lot_no` | 計画のキー |
| `is_stale` | 古い計画なら 1、そうでなければ 0。**「実績が入っていない」の条件は入っていない**（実績の扱いは現場アプリが自分の実績で決める） |
| `has_legacy_actuals` | 既存アプリ側の実績の有無（参考用）。`production_daily` の `daily_qty` の合計が 0 より大きければ 1。既存アプリの画面と同じ定義 |
| `replacement_kitting_list_no` | `is_stale = 1` のときだけ。同じ `lot_no`・`setup_file_no`・面で、最新の取り込みに入っている別のキッティングNo.（有効な計画）。**候補がちょうど1つのときだけ値が入る**。候補が0または2つ以上なら NULL。`is_stale = 0` なら NULL |
| `replacement_count` | `is_stale = 1` のときの、上の候補の数。`is_stale = 0` なら 0 |
| `latest_batch_id` | 判定に使った最新の取り込み（`kitting_plan_batches.plan_batch_id`）。無ければ NULL |
| `judge_reason` | 判定の理由。下の表 |
| `judged_at` | 最新の取り込みの `imported_at`（`YYYY-MM-DD HH:MM:SS`）。最新の取り込みが無ければ NULL。問い合わせた時刻ではない |

### judge_reason の値

| 値 | 意味 | is_stale |
|---|---|---|
| `stale` | 開始・終了が期間に収まり、最新の取り込みに無い | 1 |
| `in_latest_batch` | 最新の取り込みにある | 0 |
| `outside_period` | 開始か終了が期間の外（期間より前に始まる、期間より後に終わる）。判定しない | 0 |
| `date_unparsable` | 開始日か終了日が空、または解釈できない。判定しない | 0 |
| `no_period` | 最新の取り込みの日時が1つも解釈できず、期間が決まらない | 0 |
| `no_latest_batch` | 最新の取り込みが無い（取り込みが前月引き継ぎだけ、など） | 0 |

## 判定の決まり（D-192）

1. **最新の取り込み**: バッチの `delete_flag` が 1 でなく、`source_file` が `carry_over:` で始まらない（前月引き継ぎは数えない）取り込みのうち、`imported_at` が最新のもの。同じ時刻なら `plan_batch_id` が大きい方。
2. **期間**: その取り込みの**すべての行**（明細の `delete_flag = 1` の行も含む）の、計画開始日の最小〜計画終了日の最大。
3. 日時は `YYYY/MM/DD HH:MM:SS` にそろえて比べる（`-` は `/` に直し、秒が無ければ補い、時刻が無ければ 00:00:00）。期間の端は**時刻まで**比べる。存在しない日付・解釈できない値は判定しない（古い扱いにしない）。
4. 古い計画（`is_stale = 1`）= 有効な計画のうち、開始・終了がどちらも期間に収まり、`(kitting_list_no, lot_no)` が最新の取り込みに無いもの。

## 現場アプリが守ること

- **ビューの全件を1回だけ読む。** ビューは問い合わせのたびに全体を計算するので、1件ずつ（`WHERE kitting_list_no = ?`）引くと遅い（1件でも全件分の計算がかかる。目安：2,500行で約 0.05 秒、25,000行で約 0.7 秒）。読んだ結果をメモリに持って使う。
- **ビューが無い DB は「古い計画なし」として扱う。** ビューは、この版（5.0.0）以降の既存アプリで**その月次DB を一度開く**とできる（開くときにマイグレーション 016 が当たる。前月引き継ぎや新規作成で作った DB には最初から入っている）。既存アプリで開かれていない古い月の DB にはビューが無い（`no such table: v_plan_stale`）。既存アプリでその月を一度開けばできる。既存アプリが他の月の DB に書き込んでビューを入れることはしない。
- **最新の取り込みが一部の計画だけの CSV だと、大量に古い扱いになる。** 期間は最新の取り込みの行から決まるので、離れた計画が少数だけ入った CSV が最新になると、期間が広がり、そこに入っていない計画が `is_stale = 1` になる（模擬データで、離れた2件だけの CSV を取り込むと、有効な計画 1034 件のうち 1030 件）。運用は「毎回、同じ長さの期間の計画をすべて入れて取り込む」ことが前提。実績のある計画は `has_legacy_actuals` で見分けられる。
- 最新の取り込みを削除すると、1つ前の取り込みで判定し直される。ただし、取り込み直しで無効になった古い版は、バッチを削除しても有効に戻らない（既存の動き。D-192）。
- `is_active` が NULL の行は有効として扱う（`COALESCE(is_active,1)`）。

## 月次DB の版

- ビューを足したので、月次DB の版は **16**。版 16 の DB は 4.x 以前の .exe では開けない（「アプリを最新版に更新してください」）。
- `kitting_plan_items`・`kitting_plan_batches`・`production_daily` を作り直すマイグレーションは、先にビューを消してから作り直し、最後にビューを作り直すこと（`docs/db.md`）。
